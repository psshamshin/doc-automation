# AGENTS.md - doc-automation (LUNA POINT 2)

Проект готовит правки документации LUNA POINT 2 (RU и EN) и release notes по изменениям фронтенда.
Что и зачем: `README.md`. Правила отбора и написания: `docs/RULES.md`.

## Как устроена работа

1. Код собирает изменения, применяет правила и пишет черновик: `python3 -m pipeline collect <набор>`.
2. Человек проверяет решения в `output/<набор>/validation.txt`.
3. Агент получает отдельные задания: `python3 -m pipeline agent <набор>`.

Агент не проходит релиз целиком. Каждое задание - отдельный запуск с готовым текстом из
`output/<набор>/agent/tasks/`. Виды заданий и шаблоны лежат в `agent/prompts/`:

| Задание | Что сделать |
| --- | --- |
| `decide` | Проверить по коду решение, достоверность которого низкая (критерии группы И) |
| `write_doc` | Написать правку документации RU, затем EN |
| `check_doc` | Исправление ошибки: проверить, не описано ли в документации старое поведение |
| `check_langs` | Сверить список языков интерфейса |
| `release_notes` | Привести черновик release notes к языку пользователя и перевести |

Результат каждого задания - файл ответа JSON в `output/<набор>/agent/answers/`. Без него задание
считается невыполненным.

## Запреты

- Не читать документацию техписа до сравнения: `input/*/docs-reference/`, `output/*/reference/`,
  `output/*/compare/`. Иначе эксперимент не имеет смысла.
- Менять только файлы в `output/<набор>/result/` и свой файл ответа. Не трогать `input/`, `pipeline/`,
  `knowledge/`, `tests/`.
- Не трогать ES, PT и другие языки: их переводит существующий джоб `translate-diff`.
- Не выдумывать. Факт берется только из кода, списка изменений и Jira. Нет факта - статус `needs_human`
  и вопрос в ответе, а не догадка.

Те же запреты записаны в `agent/settings.json`, с ним запускается агент.

## Правила написания (группы Ж и З, полный текст в docs/RULES.md)

- Ж1. Сначала RU, затем EN с тем же смыслом.
- Ж2. Названия элементов интерфейса - дословно из файлов переводов нужного языка
  (`data/03_i18n_rows.json`, поле `new`), в кавычках, как принято в документации.
- Ж3. Названия продуктов и компонентов - только через переменные документации (`{{PRODUCT_NAME}}` и
  подобные). Без жестких «LUNA» и «VisionLabs» в новом тексте.
- Ж4. Стиль как в соседних абзацах.
- Ж5. Минимальная правка: незатронутый текст не переписывать.
- Ж6. Каждая правка - строка в `result/trace.md`.
- Ж7. Если текст раздела лежит в `includes/`, править include-файл.
- Ж8. Release notes: структура как в файле прошлого релиза, одна строка на задачу, язык пользователя.
- З1, З4. Если изменение затрагивает экран со скриншота, перед картинкой ставится метка
  `!!! warning "SCREENSHOT-TODO GUI-xxxx"` и добавляется строка в `result/screenshots.md`. Старая
  ссылка на картинку не удаляется, кроме случая удаленной функции.

## Разработка

- Python 3.9+, без сторонних пакетов. Тесты: `python3 -m unittest discover -s tests`.
- Постоянные имена папок и компонентов: `pipeline/product.py`. Настроек релиза нет, версии читаются из данных.
- Изменение правила записывается в `docs/RULES.md` и в `_changes` в `knowledge/rules.json`.
- В новом тексте не использовать букву «е с двумя точками» и длинные тире.
- В git не попадают `input/` и `output/`. В тестах только придуманные данные из `tests/data/`.
