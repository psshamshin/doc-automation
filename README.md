# doc-automation

[![Tests](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml/badge.svg)](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml)

## 1. Что это и зачем

Перед каждым релизом LUNA POINT 2 технический писатель вручную выясняет, что изменилось в интерфейсе, и
правит документацию и release notes. Этот проект делает черновую часть работы сам: читает список изменений
фронтенда, сравнивает код двух версий, отбирает то, что увидит пользователь, и собирает черновик. Человек
проверяет черновик, после этого подключается ИИ-агент: он проверяет спорные решения и пишет текст правок
на русском и английском.

Нужен только Python 3.9 или новее. Сторонних пакетов нет. Файлов настроек тоже нет: все версии пайплайн
находит сам.

## 2. Как это работает

```
input/<набор>/                       положить данные
      |
      v
1. collect    код                    собрать изменения, применить правила, собрать черновик
      |
      v
   draft.md, validation.txt          человек читает черновик и проверяет решения
      |
      v
2. agent      ИИ-агент               проверить спорные решения, написать текст
      |
      v
   result/                           правки документации RU/EN и release notes
      |
      v
3. compare    код                    сравнить с документацией техписа (если она есть)
```

| Шаг | Что делает | Что получается |
| --- | --- | --- |
| `collect` | Определяет версии. Читает список изменений в границах релиза, сравнивает две папки с кодом, выясняет, какие файлы использует приложение POINT 2, достает тексты интерфейса, читает выгрузку Jira. По правилам решает для каждой задачи: наш ли это продукт, видит ли это пользователь, что это за изменение. Оценивает, насколько решение надежно. Обновляет версию интерфейса в документации и собирает черновик release notes | `draft.md`, `validation.txt`, `report.md`, рабочая копия документации в `result/` |
| проверка | Человек читает `draft.md`, правит решения в `validation.txt` и ставит `approved: yes` | одобренный `validation.txt` |
| `agent` | Раздает агенту отдельные задания и проверяет, что на каждое есть ответ | правки в `result/`, ответы и итог в `agent/` |
| `compare` | Сравнивает результат с документацией, которую написал техпис | `compare/` |

## 3. Что делает код, а что агент

Агент нужен только там, где правила не сработали или где нужно написать текст.

| Задача | Код | Агент |
| --- | --- | --- |
| Определить версии релиза, интерфейса и документации | да | |
| Выбрать изменения в границах релиза, сравнить код | да | |
| Решить, относится ли задача к POINT 2 и видит ли ее пользователь | да, по правилам | только если достоверность решения низкая |
| Оценить достоверность решения | да | |
| Подсказать страницы документации | да, по карте | находит точное место |
| Обновить версию интерфейса в документации | да | |
| Собрать черновик release notes из списка изменений | да | переписывает языком пользователя и переводит |
| Написать текст правок RU и EN | | да |
| Проверить документацию после исправления ошибки | ищет старые тексты | да, если тексты нашлись |
| Отметить скриншоты к пересъемке | | да |
| Снять скриншоты | | нет, это делает человек |
| Сравнить с документацией техписа | да | |

**Достоверность решения.** Правила всегда выдают какое-то решение. Достоверность низкая, если правила не
сработали или решение опирается только на косвенные признаки: например, на слова в записи, которые код не
подтверждает. Такие задачи получают в `validation.txt` решение `agent`: их проверяет агент. Точные
критерии: [docs/RULES.md](docs/RULES.md), группа И.

Код работает одинаково при каждом запуске: те же входные данные дают те же файлы байт в байт.


## 5. Как запустить локально

### Шаг 0. Положить данные

Создайте папку `input/<имя набора>/` (имя любое, например `2.4.0`) и в ней пять папок:

| Папка | Что положить | Откуда взять |
| --- | --- | --- |
| `source-code-old` | Исходный код фронтенда предыдущего релиза | GitLab, репозиторий фронтенда -> тег предыдущего релиза -> Download zip |
| `source-code-new` | Исходный код фронтенда нового релиза | то же, тег нового релиза |
| `docs-previous-release` | Документация предыдущего релиза | GitLab, репозиторий документации -> тег -> Download zip |
| `docs-reference` | Документация нового релиза от техписа. Нужна только для сравнения, можно не класть | то же, тег нового релиза |
| `jira-tasks` | Выгрузка задач Jira. Можно оставить пустой | см. раздел 8 |

Архив распаковывается прямо в нужную папку как есть. Переименовывать ничего не нужно.

Проверьте, что данные лежат правильно и версии определились:

```bash
python3 -m pipeline versions 2.4.0
```

### Шаг 1. Собрать изменения и черновик

```bash
python3 -m pipeline collect 2.4.0
```

Откройте `output/2.4.0/draft.md`. В нем: какие версии определились, что код уже сделал, решения по всем
задачам и достоверность каждого решения.

### Шаг 2. Проверить решения

Откройте `output/2.4.0/validation.txt`. Каждая строка - задача и решение. Если не согласны, поменяйте
слово во второй колонке. Когда все проверено, замените `approved: no` на `approved: yes`.

| Решение | Что значит | Что сделает агент |
| --- | --- | --- |
| `doc` | Править документацию и добавить строку в release notes | Напишет текст правки |
| `rn` | Только строка в release notes (исправление ошибки) | Проверит документацию, если в ней нашлись старые тексты интерфейса |
| `langs` | Строка в release notes и проверить список языков | Сверит список языков |
| `screens` | Текст не менять, проверить скриншоты | Ничего |
| `skip` | Не брать в работу | Ничего |
| `agent` | Решение не подтверждено | Проверит по коду и решит сам |

Повторный `collect` ваши правки не затирает. Если правила изменились и предложения стали другими,
одобрение снимается, а ваши решения по неизменившимся задачам сохраняются.

### Шаг 3. Запустить агента

```bash
python3 -m pipeline agent 2.4.0 --dry-run   # только подготовить задания и посмотреть, что получит агент
python3 -m pipeline agent 2.4.0             # запустить
```

Без `approved: yes` команда не запустится. Нужен установленный Claude Code (команда `claude`). Если его
нет, задания все равно готовятся в `output/2.4.0/agent/tasks/`: их можно выполнить любым агентом вручную.
Итог работы: `output/2.4.0/agent/summary.md`, правки в `output/2.4.0/result/`.

Повторный запуск выполняет только невыполненные задания. Выполнить все заново: `--redo`.

### Шаг 4. Сравнить с документацией техписа

```bash
python3 -m pipeline compare 2.4.0
```

### Запуск без входных папок

В проекте есть маленькие придуманные данные. На них можно проверить, что все работает:

```bash
python3 -m unittest discover -s tests
python3 -m pipeline collect tests/data/demo
```

Как убедиться, что результат совпадает с ожидаемым: [docs/VERIFY.md](docs/VERIFY.md).

## 6. Откуда берутся версии и настройки

Файла настроек нет. Все, что раньше задавалось вручную, пайплайн находит сам:

| Что | Откуда берется |
| --- | --- |
| Версия интерфейса: было и стало | Поле `version` в `apps/point/package.json` в папках `source-code-old` и `source-code-new` |
| Версия документации предыдущего релиза | Заголовок последнего файла release notes в `docs-previous-release`, например `# [2.2.0] 14.09.2026` |
| Версии компонентов прошлого релиза | Таблица в том же файле release notes |
| Версия нового релиза | По порядку: параметр `--release`; база знаний (по версии интерфейса); release notes техписа в `docs-reference`; иначе следующая версия после предыдущей, с предупреждением в черновике |
| Дата релиза | База знаний или release notes техписа. Если неизвестна, в черновике стоит `ДД.ММ.ГГГГ` |
| Имя файла release notes | Из версии: 2.3.0 -> `230.md` |
| Границы списка изменений | Версии интерфейса выше старой и не выше новой |

Если версия нового релиза определилась неверно, укажите ее один раз:

```bash
python3 -m pipeline collect 2.4.0 --release 2.4.0
```

Она запишется в базу знаний, и в следующих запусках параметр не нужен.

### База знаний

Папка `knowledge/` хранится в git и общая для всех релизов.

| Файл | Что внутри | Как пополняется |
| --- | --- | --- |
| `releases.json` | Какой версии продукта какая версия интерфейса соответствует, даты релизов, версии компонентов | Командой `python3 -m pipeline learn <набор>` (читает все release notes из документации) и параметром `--release` |
| `rules.json` | Списки слов, шаблоны имен файлов, признаки других продуктов, история изменений правил | Вручную, см. раздел 9 |
| `doc_map.json` | Какая часть интерфейса на какой странице документации описана | Вручную |

### Что зашито в код

Имена папок, путь к списку изменений, языки документации, имя компонента интерфейса в таблице версий
(`point-ui`) и переменная с версией в руководстве администратора (`SECURE_CLIENT_VER`) записаны в
`pipeline/product.py`. Они меняются, только если изменится устройство репозиториев.

### Необязательный файл dataset.json

Если для одного набора данных нужно что-то переопределить, положите в его папку файл `dataset.json`.
Обычно он не нужен.

| Поле | Что задает |
| --- | --- |
| `release` | Версия нового релиза |
| `release_date` | Дата релиза в виде `ДД.ММ.ГГГГ` |
| `doc_map` | Путь к своей карте документации внутри набора данных |
| `reference_ignore` | Файлы документации техписа, которые не нужно учитывать при сравнении |

### Параметры команд

| Параметр | Команда | Что делает |
| --- | --- | --- |
| `--out <папка>` | все | Писать результаты в другую папку вместо `output/<набор>` |
| `--release <версия>` | `collect` | Задать версию нового релиза и запомнить ее в базе знаний |
| `--force` | `collect` | Пересоздать рабочую копию документации и файл проверки. Стирает правки агента и человека |
| `--dry-run` | `agent` | Только подготовить задания |
| `--approve` | `agent` | Считать решения одобренными без правки `validation.txt` |
| `--redo` | `agent` | Выполнить заново уже выполненные задания |
| `--cmd "<команда>"` | `agent` | Запускать другого агента. Команда получает текст задания на стандартный ввод |
| `--timeout <секунды>` | `agent` | Время на одно задание, по умолчанию 1800 |

## 7. Как читать результаты

Читать в таком порядке: `draft.md` -> `validation.txt` -> при вопросах `report.md`.

- `draft.md` - короткий черновик: версии, что сделал код, таблица решений, задачи с низкой достоверностью
  решения и причина, по каждой задаче в работе страницы и изменившиеся тексты интерфейса.
- `report.md` - подробности по каждой задаче: все записи списка изменений, файлы, тексты.

В таблицах рядом с решением стоят коды правил, например `в доку + RN (В5, Г1, Д3)`. Буква - группа правил:
В - продукт, Г - видимость, Д - вид изменения, И - достоверность. `В5` значит «файлы задачи использует
приложение POINT 2», `Г1` - «изменились тексты интерфейса», `Д3` - «изменение поведения». Расшифровка
всех кодов: [docs/RULES.md](docs/RULES.md).

У записи может стоять пометка «не учитывается: техническая», «тест» или «другой продукт». Такая запись на
решение не влияет.

## 8. Как выгрузить задачи из Jira

После `collect` в папке результатов лежит `jira_query.txt` с готовым запросом вида `key in (GUI-1, GUI-2)`.

1. Откройте Jira -> Фильтры -> Расширенный поиск задач.
2. Вставьте запрос из `jira_query.txt` и нажмите «Найти».
3. Справа вверху: Экспорт -> XML (или CSV, все поля).
4. Положите файл в `input/<набор>/jira-tasks/` и запустите `collect` еще раз.

Из выгрузки используется название задачи и описание. Продукт определяется по метке в квадратных скобках
в начале названия: `[point] ...` - POINT 2, другая метка - другой продукт.

## 9. Правила

Все правила с примерами и историей изменений: [docs/RULES.md](docs/RULES.md).

Как добавить или поменять правило:

1. Поправить `knowledge/rules.json` или `pipeline/units.py`.
2. Записать изменение в `docs/RULES.md` (раздел «История изменений») и в поле `_changes` в
   `knowledge/rules.json`: что было, что стало, на какой задаче нашлась ошибка. Старую формулировку не
   удалять, номера правил не менять.
3. Добавить тест в `tests/test_rules.py` на придуманном примере.
4. Перезапустить на реальных данных и сравнить таблицу решений с предыдущей (см. `docs/VERIFY.md`).

## 10. Новый релиз или другие исходные данные

1. Создать `input/<имя>/` и разложить данные по пяти папкам (раздел 5, шаг 0).
2. `python3 -m pipeline versions <имя>`: проверить версии.
3. `python3 -m pipeline collect <имя>`. Если версия нового релиза не определилась, добавить `--release`.

Править код и настройки не нужно. Наборы данных не мешают друг другу: у каждого своя папка результатов.

## 11. Задачи в CI

CI - это автоматические задачи, которые GitHub запускает на своих серверах. В проекте их три.
Смотреть и запускать: страница репозитория -> вкладка Actions.

| Задача | Когда запускается | Что делает |
| --- | --- | --- |
| Tests | Сама, при каждом изменении кода | Проверяет, что код компилируется, тесты проходят и пайплайн отрабатывает на придуманных данных |
| 1. Сбор изменений | Вручную, кнопкой Run workflow | Запускает `collect` и показывает черновик на странице запуска |
| 2. Работа агента | Вручную, после проверки черновика | Требует галочку «проверил и согласен». Готовит задания агенту |

Ограничения на сегодня:

- Задачи 1 и 2 работают только на придуманных данных. Настоящих кода и документации в этом репозитории
  нет, и GitHub до них не дотянется.
- Задача 2 только готовит задания (режим `--dry-run`): ключ доступа к агенту в репозиторий не добавлен.
- На настоящих данных обе задачи сейчас запускаются локально, командами из раздела 5.

Чтобы задачи заработали на настоящих данных, нужно решить, где они будут выполняться: в GitLab компании
рядом с репозиториями кода и документации или на своей машине, подключенной к GitHub.

## 12. Ограничения

- **Файлы делятся между задачами неточно.** Истории git нет, есть только две папки с кодом. Файл
  привязывается к задаче по тегам и именам из списка изменений. Если две задачи трогали одну папку, файлы
  и изменившиеся тексты попадут к обеим. Такие случаи отмечает критерий И4.
- **Сгенерированный код API не виден.** Изменения в клиенте API, который собирается из схемы сервера, в
  сравнение не попадают.
- **Jira пока не подключена.** Правила, которые определяют продукт по названию задачи (В1, В2), не
  работают, пока в папке `jira-tasks` нет выгрузки.
- **Связи между файлами определяются приближенно.** Код разбирается регулярными выражениями, без сборки
  проекта. Импорты, которые не удалось разобрать, перечислены в отчете.
- **Правила опираются на слова в списке изменений.** Если запись написана необычно, достоверность решения
  будет низкой и задача уйдет агенту.
- **Агент на настоящих данных еще не запускался.** Обертка проверена тестами с заглушкой вместо агента.
- **Версии остальных компонентов в release notes берутся из прошлого релиза.** Во фронтенде их нет,
  в черновике стоит пометка «проверить».
