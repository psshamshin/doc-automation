# doc-automation

[![Tests](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml/badge.svg)](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml)

Готовит правки документации LUNA POINT 2 (RU и EN) и release notes по изменениям фронтенда. Код сравнивает две
версии кода и список изменений, отбирает то, что увидит пользователь, и собирает файл для проверки. После вашей
проверки агент пишет правки, а код проверяет и вносит их. Нужен Python 3.9+, сторонних пакетов нет.

## Как это работает

```
input/ (архивы)  ->  collect  ->  review.md  ->  вы проверяете  ->  agent  ->  result/ + журнал  ->  compare
                      код                         один раз          агент и код
```

1. **collect** (код): версии, изменения, решения по правилам, поиск устаревших названий, сквозные проверки документации.
   Результат - `review.md` и рабочая копия документации `result/` с обновленной версией интерфейса.
2. **Вы проверяете `review.md`**: единственное место, где нужен человек. Дальше вас ни о чем не спрашивают.
3. **agent**: код готовит агенту задания в отдельной папке, агент отвечает файлами, код проверяет ответы и вносит
   правки. Ответ не прошел проверку - одна повторная попытка с причинами; снова не прошел - ничего не вносится.
4. **compare**: сравнение с документацией техписа, если она есть.

Код работает одинаково при каждом запуске: те же данные дают те же файлы.

## Быстрый старт

```bash
git clone https://github.com/psshamshin/doc-automation.git && cd doc-automation
python3 -m unittest discover -s tests            # проверка, что все работает
```

1. Положите в `input/` архивы из GitLab (тег -> Download zip): код фронтенда предыдущего и нового релиза, документацию
   предыдущего релиза; по желанию - выгрузку Jira. Имена и вложенные папки не важны: что есть что, определяется по
   содержимому, старое и новое - по версиям. Архивы распаковываются сами.
2. `python3 -m pipeline versions` - что нашлось и какие версии определились.
3. `python3 -m pipeline collect` - результат в `output/<версия релиза>/`.
4. Откройте `review.md` (см. ниже), поставьте `Проверено: [x]`.
5. `python3 -m pipeline agent` - готовит папку агента `output/<версия>/agent_workspace/`.
6. Откройте в редакторе **только эту папку** и дайте агенту задания из `tasks/` по порядку из `AGENTS.md`
   (запрос: «Прочитай AGENTS.md и выполни задания из папки tasks по порядку»).
7. `python3 -m pipeline agent` еще раз - код проверит ответы и внесет правки. Если появились задания `__retry`,
   дайте агенту их и снова запустите `agent`.
8. Результат: `output/<версия>/result/` (документация, `trace.md`, `screenshots.md`), журнал `agent/summary.md`.
9. Сравнение: `python3 -m pipeline compare --reference /путь/к/документации/техписа`, затем
   `output/<версия>/compare/compare.html` (три колонки: было, пайплайн, техпис).

Если в `input/` несколько наборов, каждый кладется в свою папку `input/<имя>/`, и имя указывается в командах.

## review.md

Один файл для проверки. Сверху версии и что уже сделал код. Дальше:

- **Таблица задач**: у каждой ссылка на Jira, краткое описание, решение правил с кодами (расшифровка в
  [docs/RULES.md](docs/RULES.md)), основание для проверки и три отметки: «Принять», «Отклонить», «Агенту». Отметка
  уже стоит: «Принять», если решение подтверждено, «Агенту», если нет. «Отклонить» - задачу в работу не брать; если
  правила ее отбросили, ее проверит агент. Переставьте отметки, где не согласны.
- **Release notes**: что в них войдет (записи разработчиков и раздел). Формулировки напишет агент.
- **Сквозные проверки** и **названия, которых больше нет в интерфейсе**: итоги; подробности в `checks.md`.
- **Задачи Jira вне списка изменений**, если есть выгрузка.

Решения правил: `в доку + RN` - править документацию и добавить строку; `RN + проверить доку` - исправление, только
строка; `RN + проверить список языков` - изменился набор языков; `проверить скрины` - только оформление;
`не определено` - правила не решили; `отброшено` - другой продукт или не видно пользователю.

Повторный `collect` ваши отметки не затирает; если решения правил изменились, отметка «Проверено» снимается.

## Агент

Агент работает в отдельной папке, где есть только задания, документация (для чтения) и источники своих задач:
сводка измененных строк кода `changes.md` и патчи. Правил отбора, кода пайплайна и документации техписа там нет.
Агент **не меняет файлы**: правку он описывает в ответе (страница, точный фрагмент, новый текст), вносит ее код.

Код отклоняет ответ целиком, если: цитаты нет в источнике (регистр не важен, допустима опечатка в одну-две буквы); в
шагах файл вне источников задачи; страница не входит в задание; заменяемый фрагмент не найден или повторяется; в новом
тексте название в кавычках, которого нет в интерфейсе новой версии, комментарий, метка скриншота или больше 30 строк.
Release notes: у каждой принятой задачи должна быть одна строка RU и EN либо причина в `no_line`.

Задания: `decide` (решение с низкой достоверностью), `write_doc` (правка документации), `stale_names` (одно задание на
весь релиз: устаревшие названия, для каждого указаны файлы кода, где оно использовалось), `release_notes`. Каждое
задание ждет ответа в `answers/`. Ход работы агент дописывает в `progress.md`. Журнал по заданиям:
`agent/summary.md` (состояние, внесенные правки, причины отказов, шаги, время).

Команду запуска агента можно задать параметром `--cmd` или переменной `DOC_AGENT_CMD`: она получает текст задания на
стандартный ввод и запускается в папке агента. Без нее задания только готовятся.

**Чистый эксперимент.** Документацию техписа агент видеть не должен. Команда `agent --cmd` не запускается, пока она
лежит в `input/`, `reference/` или в результатах сравнения. При ручном запуске следите сами: держите ее вне проекта и
передавайте в `compare --reference`.

## Сквозные проверки и скриншоты

Не привязаны к задачам, выполняются кодом, агент не нужен (правила К1-К5):

- **Битые ссылки**: страница, якорь или подключаемый файл, которых нет.
- **Названия продуктов текстом**: «LUNA» и «VisionLabs» вместо переменных.
- **Расхождения языков**: страницы, разделы, картинки, версии компонентов.
- **Картинки**: ссылка без файла; картинка без ссылок; не подключенный файл из `includes`.
- **Скриншоты к проверке**: изменился текст раздела - скриншоты раздела в списке `result/screenshots.md`.

Итог в `review.md`, подробности в `checks.md`; у каждой находки отмечено, появилась она в этом релизе или была раньше.
Проверки пересчитываются после работы агента: `python3 -m pipeline check`. Правок по ним код не вносит.

## Версии и база знаний

Файла настроек нет: версия интерфейса читается из `apps/point/package.json`, версия документации и таблица версий -
из последнего файла release notes, версия нового релиза - из базы знаний `knowledge/releases.json` (по версии
интерфейса). Если она не определилась, укажите один раз: `collect --release 2.4.0` - она запомнится. Остальные файлы
`knowledge/`: `rules.json` (слова и признаки правил), `doc_map.json` (страница для части интерфейса), `links.json`
(адрес задачи в Jira). Постоянные имена папок и компонентов - `pipeline/product.py`. Необязательный
`dataset.json` в наборе данных переопределяет `release`, `release_date`, `doc_map`, `jira_task_url`.

## Jira

Сначала `collect` без выгрузки: по списку изменений он составит запросы в `output/<версия>/jira_query.txt` (основной -
задачи из списка; контрольный - закрытые между релизами задачи, которых в списке нет). В Jira: Фильтры -> Расширенный
поиск, вставить запрос, Экспорт -> XML, файл положить в `input/`, запустить `collect` еще раз. Метка `[point]` в названии
значит POINT 2; метка другого продукта отбрасывает задачу, только если у нее нет кода, который использует POINT 2.

## Команды и параметры

| Команда | Что делает |
| --- | --- |
| `versions` | Показать, что нашлось и какие версии определились |
| `collect` | Сбор, правила, `review.md`. `--force` пересоздает результат и стирает работу агента, `--release` задает версию |
| `agent` | Задания, проверка ответов, внесение правок. `--cmd` запуск агента, `--dry-run` только подготовить, `--redo` заново, `--approve` без отметки «Проверено», `--timeout` секунд на задание |
| `check` | Пересчитать сквозные проверки |
| `compare` | Сравнить с документацией техписа (`--reference <папка>`) |
| `learn` | Записать релизы из release notes документации в базу знаний |

У всех команд необязательное имя набора данных и `--out <папка>` для результатов.

## CI

`Tests` запускается сама при каждом изменении: компиляция, JSON, тесты, прогон на придуманных данных. Задачи
«1. Сбор изменений» и «2. Работа агента» запускаются вручную и работают только на придуманных данных: настоящих кода
и документации в репозитории нет.

## Проект

```
input/ output/ reference/   данные и результаты (в git не попадают)
knowledge/                  правила, карта документации, релизы
pipeline/                   код; pipeline/agent/ - задания, проверка ответов, запуск
agent/prompts/              правила и формат ответа агента
tests/                      тесты и придуманные данные tests/data/demo
docs/                       RULES.md (правила), VERIFY.md (как проверить), TODO.md (отложено)
```

## Ограничения

- Файлы делятся между задачами неточно: истории git нет, привязка идет по тегам списка изменений.
- Часть исчезнувших названий не имеет замены в данных (убраны вместе с неиспользуемыми ключами переводов).
- Проверка кода не оценивает смысл: она убеждается, что цитата, название и фрагмент существуют.
- Названия задач в Jira внутренние, в release notes не идут.
- Языки интерфейса, доступные пользователям, из кода не видны.
