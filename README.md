# doc-automation

[![Tests](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml/badge.svg)](https://github.com/psshamshin/doc-automation/actions/workflows/tests.yml)

## 1. Что это и зачем

Перед каждым релизом LUNA POINT 2 технический писатель вручную выясняет, что изменилось в интерфейсе, и
правит документацию и release notes. Этот проект делает черновую часть работы сам: читает список изменений
фронтенда, сравнивает код двух версий, отбирает то, что увидит пользователь, и собирает один файл для
проверки. Человек отмечает в нем, с чем согласен. После этого подключается ИИ-агент: он проверяет только
те решения, которые не подтвердились, и пишет текст правок на русском и английском.

Нужен только Python 3.9 или новее. Сторонних пакетов нет. Файлов настроек тоже нет: все версии пайплайн
находит сам.

## 2. Как это работает

```
input/<набор>/                       положить данные
      |
      v
1. collect    код                    собрать изменения, применить правила, собрать черновик
      |
      v
   review.md                         человек проверяет решения: принять, отклонить, агенту
      |
      v
2. agent      ИИ-агент               проверить спорные решения, написать текст
      |
      v
   result/                           правки документации RU/EN и release notes
      |
      v
3. compare    код                    сравнить с документацией техписа (если она есть)
```

| Шаг | Что делает | Что получается |
| --- | --- | --- |
| `collect` | Определяет версии. Читает список изменений в границах релиза, сравнивает две папки с кодом, выясняет, какие файлы использует приложение POINT 2, достает тексты интерфейса, читает выгрузку Jira. По правилам решает для каждой задачи: наш ли это продукт, видит ли это пользователь, что это за изменение. Оценивает, насколько решение надежно. Обновляет версию интерфейса в документации и собирает черновик release notes | `review.md`, `report.md`, рабочая копия документации в `result/` |
| проверка | Человек открывает `review.md`, переставляет отметки, где не согласен, и ставит «Проверено» | проверенный `review.md` |
| `agent` | Собирает для агента отдельную папку с заданиями и источниками, проверяет цитаты в ответах, принимает только подтвержденные правки | правки в `result/`, журнал в `agent/summary.md` |
| `compare` | Сравнивает результат с документацией, которую написал техпис | `compare/` |

## 3. Что делает код, а что агент

Агент нужен только там, где правила не сработали или где нужно написать текст.

| Задача | Код | Агент |
| --- | --- | --- |
| Определить версии релиза, интерфейса и документации | да | |
| Выбрать изменения в границах релиза, сравнить код | да | |
| Решить, относится ли задача к POINT 2 и видит ли ее пользователь | да, по правилам | только если достоверность решения низкая |
| Оценить достоверность решения | да | |
| Подсказать страницы документации | да, по карте | находит точное место |
| Обновить версию интерфейса в документации | да | |
| Собрать черновик release notes из списка изменений | да | переписывает языком пользователя и переводит |
| Написать текст правок RU и EN | | да |
| Проверить документацию после исправления ошибки | ищет старые тексты | да, если тексты нашлись |
| Отметить скриншоты к пересъемке | | да |
| Снять скриншоты | | нет, это делает человек |
| Сравнить с документацией техписа | да | |

**Достоверность решения.** Правила всегда выдают какое-то решение. Достоверность низкая, если правила не
сработали или решение опирается только на косвенные признаки: например, на слова в записи, которые код не
подтверждает. У таких задач в файле проверки по умолчанию стоит отметка «Агенту». Точные
критерии: [docs/RULES.md](docs/RULES.md), группа И.

Код работает одинаково при каждом запуске: те же входные данные дают те же файлы байт в байт.

## 4. Структура проекта

```
doc-automation/
├── input/              сюда кладутся архивы с кодом и документацией (в git не попадают)
├── output/<релиз>/     результаты прогона (в git не попадают)
├── reference/          документация техписа для сравнения, кладется после работы агента (в git не попадает)
├── knowledge/          база знаний: правила, карта документации, список релизов, адрес Jira
├── pipeline/           код
├── agent/              шаблоны заданий агенту и его ограничения
├── tests/              тесты и придуманные данные tests/data/demo
├── docs/               RULES.md - правила, VERIFY.md - как проверить результат
└── .github/workflows/  автоматические задачи GitHub
```

## 5. Как запустить локально

Короткая инструкция от клонирования до сравнения, с агентом, запускаемым вручную из редактора: [docs/QUICKSTART.md](docs/QUICKSTART.md).

### Шаг 0. Положить данные

Сложите все в одну папку `input/`. Создавать вложенные папки и переименовывать ничего не нужно.

| Что положить | Откуда взять | Обязательно |
| --- | --- | --- |
| Архив с кодом фронтенда предыдущего релиза | GitLab, репозиторий фронтенда -> тег -> Download zip | да |
| Архив с кодом фронтенда нового релиза | то же, тег нового релиза | да |
| Архив с документацией предыдущего релиза | GitLab, репозиторий документации -> тег -> Download zip | да |
| Архив с документацией нового релиза от техписа | то же, тег нового релиза. Нужен только для сравнения. Для чистого эксперимента кладется не сюда, а в `reference/` после работы агента (шаг 4) | нет |
| Выгрузка задач Jira (XML, CSV, JSON или текст) | см. раздел 8; делается после первого запуска | нет |

Архивы (`.zip`, `.tar.gz`) пайплайн распакует сам в `input/_unpacked/`. Можно класть и уже распакованные
папки. Что из этого код, а что документация, определяется по содержимому; что старое, а что новое - по
версиям внутри. Имена архивов и папок значения не имеют.

Если нужно хранить несколько наборов данных сразу, положите каждый в свою папку `input/<имя>/` и
указывайте имя в командах: `python3 -m pipeline collect <имя>`.

Проверьте, что все нашлось и версии определились:

```bash
python3 -m pipeline versions
```

### Шаг 1. Собрать изменения

```bash
python3 -m pipeline collect
```

Результаты появятся в `output/<версия релиза>/`.

### Шаг 2. Проверить решения

Откройте один файл: `output/<версия>/review.md`. В нем версии, что уже сделал код, таблица задач, строки
черновика release notes и замены названий, которые внесет код. У каждой
задачи ссылка на Jira, краткое описание, решение правил и три отметки:

| Отметка | Что значит |
| --- | --- |
| Принять | Согласен с решением правил |
| Отклонить | Не согласен: задачу в работу не брать. Если правила задачу отбросили, ее проверит агент |
| Агенту | Пусть решение проверит агент по коду |

Отметка `[x]` уже стоит: «Принять», если решение подтверждено, и «Агенту», если нет. Переставьте ее, где не
согласны, и поставьте `x` в строке «Проверено» наверху файла.

Повторный `collect` ваши отметки не затирает. Если правила изменились и решения стали другими, отметка
«Проверено» снимается, а отметки по неизменившимся задачам сохраняются.

Подробности по задаче (все записи, файлы, тексты интерфейса) лежат в `report.md`. Читать его для проверки
не обязательно.

### Шаг 3. Запустить агента

```bash
python3 -m pipeline agent
```

Без отметки «Проверено» команда не запустится. Сначала код вносит замены названий для принятых задач.
Затем он собирает для агента **отдельную папку** `output/<версия>/agent_workspace/`. Агент работает только
в ней, а не в папке проекта.

| Что в папке агента | Зачем |
| --- | --- |
| `AGENTS.md` | Общие правила для всех заданий, формат ответа, порядок действий по каждому виду задания, порядок заданий. Лежат один раз, а не в каждом задании |
| `tasks/` | Задания, по одному файлу: только данные конкретной задачи, ее страницы и источники |
| `answers/` | Сюда агент пишет ответы |
| `docs/` | Рабочая копия документации |
| `sources/<задача>/` | Патчи и файлы кода только этой задачи |

Правил отбора, кода пайплайна, списка доработок, данных других релизов и документации техписа в этой
папке нет: агенту нечего прочитать лишнего.

**Как код проверяет агента.** Агенту нельзя верить на слово, поэтому:

- Способ не зависит от агента: `AGENTS.md` - общий формат инструкций, который читают разные агенты, а
  все проверки делает код после работы агента.
- В `AGENTS.md` записан код правил. Агент обязан повторить его в каждом ответе: так видно, что общие
  правила он прочитал. Ответ без кода не принимается.
- В каждом задании перечислены разрешенные источники и страницы, которые можно менять.
- Каждое утверждение и каждую правку агент обязан подтвердить дословной цитатой из источника. Код
  проверяет, что цитата буква в букву есть в источнике. Нет цитаты или она выдумана - ответ не принят.
- В `result/` переносятся только правки из принятых ответов и только на страницах задания. Остальные
  изменения откладываются в `agent/rejected/`, а папка агента возвращается к принятому состоянию.
- По каждому заданию ведется журнал `output/<версия>/agent/summary.md`: состояние, решение, что принято,
  что отклонено и почему, ход работы со слов агента, его вопросы.

Агент пока не выбран, поэтому есть два способа запуска:

- **Вручную.** Откройте в редакторе только папку `agent_workspace` и дайте агенту задания по порядку из
  `AGENTS.md`. Потом запустите `python3 -m pipeline agent` еще раз: команда проверит ответы, перенесет
  принятые правки и подготовит следующие задания. Повторяйте, пока в журнале есть задания «ждет агента».
- **Командой.** `python3 -m pipeline agent --cmd "<команда агента>"`. Команда запускается в папке агента и
  получает текст задания на стандартный ввод.

Состояния заданий в журнале: «принято», «ждет агента», «не подтверждено» (агент должен переделать),
«нужен человек» (агент не нашел факта в источниках), «ошибка».

### Шаг 4. Сравнить с документацией техписа

```bash
python3 -m pipeline compare
open output/<версия>/compare/compare.html
```

`compare.html` - одна страница, открывается в браузере без интернета. На ней три колонки: «Было»
(документация прошлого релиза), «Пайплайн» (код и агент), «Техпис». Сверху выбирается язык и файл; можно
показать только файлы, которые изменили оба, только пайплайн или только техпис. Изменения выделены цветом:
зеленый - добавлено, красный - удалено, желтый - изменено, внутри строки выделены изменившиеся слова.
Между колонками стоит знак: `=` оба сделали одно и то же, `≠` оба изменили, но по-разному, `‹` только
пайплайн, `›` только техпис.

Сравнение показывает различия, но не оценивает смысл: качество текста проверяет человек.

**Как гарантировать, что агент не видел документацию техписа.** Запрет в инструкции агента - не гарантия.
Гарантия одна: на время работы агента этой документации нет в проекте. Поэтому команда `agent` не
запускает агента, если находит ее во входных данных, в папке `reference/` или находит результаты прошлого
сравнения в `output/<версия>/reference` и `compare`. Порядок для чистого эксперимента:

1. В `input/` только код двух версий и документация прошлого релиза. `collect`, проверка, `agent`.
2. После агента положите документацию техписа в папку `reference/` (или в любое место и укажите его:
   `compare --reference <папка>`).
3. `python3 -m pipeline compare`.
4. Перед следующим запуском агента уберите ее и результаты сравнения.

Без документации техписа версия нового релиза берется из базы знаний, а если ее там нет, указывается
один раз: `collect --release <версия>`.

### Запуск без входных папок

В проекте есть маленькие придуманные данные. На них можно проверить, что все работает:

```bash
python3 -m unittest discover -s tests
python3 -m pipeline collect tests/data/demo
```

Как убедиться, что результат совпадает с ожидаемым: [docs/VERIFY.md](docs/VERIFY.md).

## 6. Откуда берутся версии и настройки

Файла настроек нет. Все, что раньше задавалось вручную, пайплайн находит сам:

| Что | Откуда берется |
| --- | --- |
| Что код, а что документация | По содержимому: в коде есть `apps/point/package.json`, в документации `docs/src` |
| Версия интерфейса: было и стало | Поле `version` в `apps/point/package.json`: меньшая версия - предыдущий релиз, большая - новый |
| Версия документации предыдущего релиза | Заголовок последнего файла release notes, например `# [2.2.0] 14.09.2026`. Если документаций две, более старая - предыдущий релиз, более новая - от техписа |
| Версии компонентов прошлого релиза | Таблица в том же файле release notes |
| Версия нового релиза | По порядку: параметр `--release`; база знаний (по версии интерфейса); release notes в документации техписа; иначе следующая версия после предыдущей, с предупреждением в черновике |
| Дата релиза | База знаний или release notes техписа. Если неизвестна, в черновике стоит `ДД.ММ.ГГГГ` |
| Имя файла release notes | Из версии: 2.3.0 -> `230.md` |
| Границы списка изменений | Версии интерфейса выше старой и не выше новой |

Если версия нового релиза определилась неверно, укажите ее один раз:

```bash
python3 -m pipeline collect --release 2.4.0
```

Она запишется в базу знаний, и в следующих запусках параметр не нужен.

### База знаний

Папка `knowledge/` хранится в git и общая для всех релизов.

| Файл | Что внутри | Как пополняется |
| --- | --- | --- |
| `releases.json` | Какой версии продукта какая версия интерфейса соответствует, даты релизов, версии компонентов | Командой `python3 -m pipeline learn` (читает все release notes из документации) и параметром `--release` |
| `rules.json` | Списки слов, шаблоны имен файлов, признаки других продуктов, история изменений правил | Вручную, см. раздел 9 |
| `doc_map.json` | Какая часть интерфейса на какой странице документации описана | Вручную |
| `links.json` | Адрес задачи в Jira для ссылок в файле проверки | Вручную |

### Что зашито в код

Имена папок, путь к списку изменений, языки документации, имя компонента интерфейса в таблице версий
(`point-ui`) и переменная с версией в руководстве администратора (`SECURE_CLIENT_VER`) записаны в
`pipeline/product.py`. Они меняются, только если изменится устройство репозиториев.

### Необязательный файл dataset.json

Если для одного набора данных нужно что-то переопределить, положите в его папку файл `dataset.json`.
Обычно он не нужен.

| Поле | Что задает |
| --- | --- |
| `release` | Версия нового релиза |
| `release_date` | Дата релиза в виде `ДД.ММ.ГГГГ` |
| `doc_map` | Путь к своей карте документации внутри набора данных |
| `jira_task_url` | Адрес задачи в Jira для этого набора данных; пустая строка отключает ссылки |

### Параметры команд

| Параметр | Команда | Что делает |
| --- | --- | --- |
| `--out <папка>` | все | Писать результаты в другую папку вместо `output/<набор>` |
| `--release <версия>` | `collect` | Задать версию нового релиза и запомнить ее в базе знаний |
| `--force` | `collect` | Пересоздать рабочую копию документации и файл проверки. Стирает правки агента и отметки человека |
| `--dry-run` | `agent` | Только подготовить задания, даже если агент настроен |
| `--approve` | `agent` | Считать решения проверенными без отметки в `review.md` |
| `--redo` | `agent` | Выполнить заново уже выполненные задания |
| `--cmd "<команда>"` | `agent` | Команда запуска агента. Она получает текст задания на стандартный ввод |
| `--timeout <секунды>` | `agent` | Время на одно задание, по умолчанию 1800 |
| `--reference <папка>` | `compare` | Где лежит документация техписа, если ее нет во входных данных и в `reference/` |
| `--allow-reference` | `agent` | Запустить агента, даже если документация техписа лежит в проекте. Результат нельзя считать чистым |

## 7. Как читать результаты

Для проверки достаточно одного файла: `review.md`.

В колонке «Решение правил» рядом с решением стоят коды, например `в доку + RN (В5, Г1, Д3)`. Буква -
группа правил: В - продукт, Г - видимость, Д - вид изменения, И - достоверность. `В5` значит «файлы задачи
использует приложение POINT 2», `Г1` - «изменились тексты интерфейса», `Д3` - «изменение поведения».
Расшифровка всех кодов: [docs/RULES.md](docs/RULES.md).

| Решение правил | Что значит |
| --- | --- |
| в доку + RN | Пользователь увидит изменение: править документацию и добавить строку в release notes |
| RN + проверить доку | Исправлена ошибка: строка в release notes и проверка, не описано ли в документации старое поведение |
| RN + проверить список языков | Изменился набор языков интерфейса |
| проверить скрины | Изменилось только оформление: текст не трогать, проверить скриншоты |
| не определено | Правила не смогли решить |
| отброшено | Другой продукт или пользователь изменения не видит |

Колонка «Основание для проверки» заполнена, только если достоверность решения низкая.

Остальные файлы:

- `report.md` - подробности по каждой задаче. У записи может стоять пометка «не учитывается: техническая»,
  «тест» или «другой продукт»: такая запись на решение не влияет.
- `result/MD_rus/docs/release-notes/<версия>.md` - черновик release notes. Код собирает его из записей
  списка изменений по образцу прошлого релиза: заголовок, таблица версий, разделы. Формулировки в нем
  взяты у разработчиков как есть, английский файл не переведен: это доделывает агент или человек.

## 8. Как выгрузить задачи из Jira

Порядок такой: сначала пайплайн проходит по списку изменений фронтенда и выясняет, какие задачи вошли в
релиз, а потом сам составляет запросы для Jira. Поэтому первый `collect` запускается без выгрузки.

1. Запустите `python3 -m pipeline collect`.
2. Откройте `output/<версия>/jira_query.txt`. В нем два готовых запроса:
   - **основной** - задачи, названные в списке изменений: `key in (GUI-1, GUI-2, ...)`;
   - **контрольный** - задачи того же проекта, закрытые между выпусками двух версий интерфейса, которых в
     списке изменений нет. Он показывает, что разработчики могли не записать.
3. В Jira: Фильтры -> Расширенный поиск задач, вставьте запрос, нажмите «Найти».
4. Справа вверху: Экспорт -> XML.
5. Положите файлы в `input/` рядом с архивами и запустите `collect` еще раз.

Что пайплайн берет из выгрузки:

- **Продукт.** Если название задачи начинается с метки в квадратных скобках, продукт определяется по ней:
  `[point] ...` - POINT 2, другая метка - другой продукт. Если метки нет, продукт определяется по коду.
- **Строку release notes.** Название задачи идет в черновик вместо записей разработчиков.
- **Задачи вне списка изменений.** Задачи из выгрузки, которых нет в списке изменений, показаны в файле
  проверки отдельной таблицей со ссылками. Решений по ним нет: к ним не привязан код.

Окно дат для контрольного запроса берется из дат версий в списке изменений. Отбор по спринту в запрос не
включен: имена спринтов нельзя вывести из данных, а окно дат дает тот же набор задач.

## 9. Правила

Все правила с примерами и историей изменений: [docs/RULES.md](docs/RULES.md).

Как добавить или поменять правило:

1. Поправить `knowledge/rules.json` или `pipeline/units.py`.
2. Записать изменение в `docs/RULES.md` (раздел «История изменений») и в поле `_changes` в
   `knowledge/rules.json`: что было, что стало, на какой задаче нашлась ошибка. Старую формулировку не
   удалять, номера правил не менять.
3. Добавить тест в `tests/test_rules.py` на придуманном примере.
4. Перезапустить на реальных данных и сравнить таблицу решений с предыдущей (см. `docs/VERIFY.md`).

## 10. Новый релиз или другие исходные данные

1. Убрать из `input/` прошлые архивы и папку `_unpacked` (или положить новые данные в `input/<имя>/`).
2. Положить новые архивы в `input/`.
3. `python3 -m pipeline versions`: проверить версии.
4. `python3 -m pipeline collect`. Если версия нового релиза не определилась, добавить `--release`.

Править код и настройки не нужно. У каждого релиза своя папка результатов.

Идеи и отложенные доработки записаны в [docs/TODO.md](docs/TODO.md).

## 11. Задачи в CI

CI - это автоматические задачи, которые GitHub запускает на своих серверах. В проекте их три.
Смотреть и запускать: страница репозитория -> вкладка Actions.

| Задача | Когда запускается | Что делает |
| --- | --- | --- |
| Tests | Сама, при каждом изменении кода | Проверяет, что код компилируется, тесты проходят и пайплайн отрабатывает на придуманных данных |
| 1. Сбор изменений | Вручную, кнопкой Run workflow | Запускает `collect` и показывает файл проверки на странице запуска |
| 2. Работа агента | Вручную, после проверки | Требует галочку «проверил и согласен». Готовит задания агенту |

Ограничения на сегодня:

- Задачи 1 и 2 работают только на придуманных данных. Настоящих кода и документации в этом репозитории
  нет, и GitHub до них не дотянется.
- Задача 2 только готовит задания: агент пока не выбран.
- На настоящих данных обе задачи сейчас запускаются локально, командами из раздела 5.

Чтобы задачи заработали на настоящих данных, нужно решить, где они будут выполняться: в GitLab компании
рядом с репозиториями кода и документации или на своей машине, подключенной к GitHub.

## 12. Ограничения

- **Файлы делятся между задачами неточно.** Истории git нет, есть только две папки с кодом. Файл
  привязывается к задаче по тегам и именам из списка изменений. Если две задачи трогали одну папку, файлы
  и изменившиеся тексты попадут к обеим. Такие случаи отмечает критерий И4.
- **Jira пока не подключена.** Правила, которые определяют продукт по названию задачи (В1, В2), не
  работают, пока в `input/` нет выгрузки. Строки черновика release notes без нее берутся из записей
  разработчиков.
- **Связи между файлами определяются приближенно.** Код разбирается регулярными выражениями, без сборки
  проекта. Импорты, которые не удалось разобрать, перечислены в отчете.
- **Правила опираются на слова в списке изменений.** Если запись написана необычно, достоверность решения
  будет низкой и задача уйдет агенту.
- **Агент не выбран.** Подготовка папки, проверка цитат и прием правок проверены тестами с заглушкой
  вместо агента.
- **Проверка цитат не проверяет смысл.** Код убеждается, что цитата есть в источнике, но не что вывод из
  нее верен. Это проверяет человек по журналу.
- **Текст страниц документации код не пишет.** Он знает страницу, но не абзац, и не умеет формулировать.
  Механические правки код делает сам: версия интерфейса, структура release notes, замена названий
  элементов интерфейса.
- **Версии остальных компонентов в release notes берутся из прошлого релиза.** Во фронтенде их нет,
  в черновике стоит пометка «проверить».
