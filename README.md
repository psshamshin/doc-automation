# doc-automation

[![CI](https://github.com/psshamshin/doc-automation/actions/workflows/ci.yml/badge.svg)](https://github.com/psshamshin/doc-automation/actions/workflows/ci.yml)

## 1. Что это и зачем

Перед каждым релизом LUNA POINT 2 технический писатель вручную выясняет, что изменилось в интерфейсе, и
правит документацию и release notes. Этот проект делает черновую часть работы сам: читает список изменений
фронтенда и сравнивает код двух версий, отбирает то, что увидит пользователь, и готовит правки
документации на русском и английском. Сейчас это эксперимент: берем документацию версии 2.2.0, получаем
правки для 2.3.0 и сравниваем с тем, что написал технический писатель.

Нужен только Python 3.9 или новее. Сторонних пакетов нет.

## 2. Как это работает

```
список изменений + код двух версий + задачи Jira
        |
        v
  1. сбор            (код)
        |
        v
  2. отбор по правилам (код)   -> report.md
        |
        v
  3-6. агент: разбор, поиск места, правки, release notes
        |
        v
  правки доки RU/EN + release notes
        |
        v
  7. сравнение с эталоном (код)
```

| Шаг | Что делает | Что получается |
| --- | --- | --- |
| 1. Сбор (`collect`) | Читает список изменений в границах релиза, сравнивает две папки с кодом, выясняет, какие файлы использует приложение POINT 2, достает тексты интерфейса, читает выгрузку Jira | `01_changelog.json`, `02_code_diff.json`, `02_reachability.json`, `03_i18n_*.json`, `04_jira.json` |
| 2. Отбор (`classify`) | Собирает записи по задачам и по правилам решает для каждой: наш ли это продукт, видит ли это пользователь, что это за изменение | `05_units.json`, `report.md` |
| Подготовка (`docs-index`, `workspace`) | Составляет оглавление исходной документации и делает ее рабочую копию | `06_docs_index.json`, `output/` |
| 3. Разбор (агент) | По коду выясняет, что именно изменилось на экране, решает задачи, которые не решили правила | `07_analysis.json` |
| 4. Место (агент) | Находит страницу и абзац, которые нужно поправить | `08_plan.json` |
| 5. Правки (агент) | Правит рабочую копию документации: сначала RU, затем EN. Ставит метки там, где нужно переснять скриншот | файлы в `output/MD_rus`, `output/MD_eng`, `trace.md`, `screenshots.md` |
| 6. Release notes (агент) | Пишет release notes по образцу прошлого релиза | `release-notes/<версия>.md` |
| 7. Сравнение (`etalon`, `compare`) | Сравнивает результат с документацией, которую написал технический писатель | `_etalon/`, `compare/` |

Все результаты лежат в `runs/<релиз>/`.

## 3. Что делает код, а что агент

| Задача | Код | Агент |
| --- | --- | --- |
| Выбрать изменения в границах релиза | да | |
| Сравнить код двух версий | да | |
| Привязать измененные файлы к задачам | да | проверяет файлы без привязки |
| Решить, относится ли задача к POINT 2 | да, по правилам | решает спорные случаи |
| Решить, видит ли изменение пользователь | да, по правилам | решает спорные случаи |
| Определить вид изменения | черновик | уточняет по коду |
| Подсказать страницы документации | да, по карте | находит точное место |
| Написать текст правок RU и EN | | да |
| Написать release notes | | да |
| Отметить скриншоты к пересъемке | | да |
| Снять скриншоты | | нет, это делает человек |
| Сравнить с эталоном | да | |

Код работает одинаково при каждом запуске: те же входные данные дают тот же `report.md` байт в байт.
Инструкции агента: `AGENTS.md` и папка `prompts/`.

## 4. Как запустить локально

### Что положить рядом

Папки кладутся в корень проекта. В git они не попадают.

| Папка | Что это | Откуда взять |
| --- | --- | --- |
| `lerna-@vlapps-point@2.9.4` | Код фронтенда предыдущего релиза | GitLab, репозиторий фронтенда -> нужный тег -> Download zip |
| `lerna-@vlapps-point@2.11.0` | Код фронтенда нового релиза | то же, тег нового релиза |
| `luna-point-2.2.0` | Документация предыдущего релиза (с нее начинаем) | GitLab, репозиторий документации -> тег -> Download zip |
| `luna-point-2.3.0` | Документация нового релиза (эталон, только для сравнения) | то же, тег нового релиза |
| `jira/` | Выгрузка задач Jira: XML, CSV, JSON или текст. Можно оставить пустой | Jira -> Export |

Архив распаковать так, чтобы имя папки совпало с именем в таблице. Пути задаются в
`config/release-2.3.0.json`.

### Команды

```bash
# шаги 1-2, оглавление документации и рабочая копия
python3 -m pipeline.run --config config/release-2.3.0.json

# только сбор и отбор
python3 -m pipeline.run --config config/release-2.3.0.json --steps collect,classify

# после работы агента: сравнение с эталоном
python3 -m pipeline.run --config config/release-2.3.0.json --steps etalon,compare
```

Флаг `--force` пересоздает рабочую копию документации в `output/` и стирает правки агента. Без него
существующая копия не трогается.

### Запуск без входных папок

В проекте есть маленькие придуманные данные. На них можно проверить, что все работает:

```bash
python3 -m unittest discover -s tests
python3 -m pipeline.run --config config/release-fixture.json --force
```

Как убедиться, что результат совпадает с моим: [docs/VERIFY.md](docs/VERIFY.md).

## 5. Как читать отчет

Главный файл - `runs/<релиз>/report.md`. Сверху сводка, затем таблица по задачам, затем подробности по
каждой задаче: записи из списка изменений, файлы, изменившиеся тексты интерфейса, страницы-кандидаты.

Решения:

| Решение | Что значит | Что делает агент |
| --- | --- | --- |
| в доку + RN | Пользователь увидит изменение | Правит документацию и пишет строку в release notes |
| RN + проверить доку | Исправлена ошибка | Пишет строку в release notes и проверяет, не описано ли в документации старое, ошибочное поведение |
| RN + проверить список языков | Изменился набор языков интерфейса | Пишет строку в release notes и сверяет список языков в документации |
| проверить скрины | Изменился только внешний вид | Текст не трогает, отмечает скриншоты к пересъемке |
| нужна проверка (не определено) | Правила не смогли решить | Решает сам по коду |
| отброшено | Другой продукт или пользователь изменения не видит | Ничего |

Коды в скобках показывают, какое правило сработало. Например, `point2 (В5)`: задача относится к POINT 2,
потому что ее файлы использует приложение. `visible (Г1)`: изменение видно, потому что поменялись тексты
интерфейса. `Д8` - вид изменения: исправление ошибки. Буква - группа правил: В - продукт, Г - видимость,
Д - вид изменения. Расшифровка всех кодов: [docs/RULES.md](docs/RULES.md).

У записи в подробностях может стоять пометка «не учитывается: техническая», «тест» или «другой продукт».
Такая запись на решение не влияет.

## 6. Правила

Все правила с примерами и историей изменений: [docs/RULES.md](docs/RULES.md).

Где что лежит:

- `config/rules.json` - списки слов, шаблоны имен файлов, признаки других продуктов;
- `config/doc_map.json` - какая часть интерфейса на какой странице документации описана;
- `pipeline/units.py` - порядок применения правил.

Как добавить или поменять правило:

1. Поправить `config/rules.json` или `pipeline/units.py`.
2. Записать изменение в `docs/RULES.md` (раздел «История изменений») и в поле `_changes` в
   `config/rules.json`: что было, что стало, на какой задаче нашлась ошибка. Старую формулировку не
   удалять, номера правил не менять.
3. Добавить тест в `tests/test_rules.py` на придуманном примере.
4. Перезапустить на реальных данных и сравнить таблицу решений с предыдущей (см. `docs/VERIFY.md`).

## 7. Новый релиз

1. Скопировать `config/release-2.3.0.json` в `config/release-<версия>.json`.
2. Поменять в нем: `release`, `docs_base_version`, границы версий интерфейса (`ui_version_lower`,
   `ui_version_upper`), пути к четырем папкам, `run_dir`, `component_versions`, блок `release_notes`.
3. Очистить `etalon_ignore`: это список правок эталона, не связанных с задачами.
4. Положить рядом новые папки с кодом и документацией.
5. Запустить с новым конфигом.

Правила и карта документации общие для всех релизов.

## 8. CI

При каждом пуше в `main` и в каждом pull request GitHub Actions:

1. проверяет, что весь код компилируется;
2. проверяет, что все JSON в `config/` и `schemas/` читаются;
3. запускает тесты;
4. прогоняет пайплайн целиком на придуманных данных;
5. сохраняет `report.md` этого прогона как артефакт.

В CI только придуманные данные из `tests/fixtures/`: маленькая монорепа на двух версиях и мини-дока.
Настоящий код фронтенда и настоящая документация внутренние, в этот репозиторий они не попадают, как и
папка `runs/` с результатами (в ней фрагменты кода).

## 9. Ограничения

- **Файлы делятся между задачами неточно.** Истории git нет, есть только две папки с кодом. Файл
  привязывается к задаче по тегам и именам из списка изменений. Если две задачи трогали одну папку, файлы
  попадут к обеим.
- **Сгенерированный код API не виден.** Изменения в клиенте API, который собирается из схемы сервера, в
  сравнение не попадают.
- **Jira пока не подключена.** Правила, которые определяют продукт по названию задачи (В1, В2), не
  работают, пока в папке `jira/` нет выгрузки.
- **Связи между файлами определяются приближенно.** Код разбирается регулярными выражениями, без сборки
  проекта. Импорты, которые не удалось разобрать, перечислены в отчете.
- **Правила опираются на слова в списке изменений.** Если запись написана необычно, задача уйдет агенту с
  решением «нужна проверка».
