# Рабочая папка агента: релиз {{RELEASE}}

Ты помогаешь обновлять документацию LUNA POINT 2. Что изменилось в релизе, уже выяснил код. Тебе даны
задания: по каждому нужно вернуть ответ в виде файла JSON.

**Ты ничего не меняешь в документации сам.** Все файлы в `docs/` только для чтения. Правку ты описываешь
в ответе: какой фрагмент страницы заменить и на что. Код проверит ее и внесет сам. Изменения, сделанные
в файлах `docs/` напрямую, будут отброшены.

| Папка | Что внутри |
| --- | --- |
| `tasks/` | Задания. В каждом данные одной задачи, ее страницы и источники |
| `answers/` | Сюда записывается ответ на каждое задание. Единственное место, куда ты пишешь, кроме `progress.md` |
| `docs/` | Документация RU и EN. Только для чтения |
| `sources/<задача>/` | Изменения кода по одной задаче |

## Правила работы с источниками

1. Работай только с тем, что перечислено в задании в разделах «Страницы документации этой задачи» и
   «Разрешенные источники». Другие файлы не открывай и не ищи по папке: все, что относится к задаче, уже
   найдено и дано тебе.
2. Каждое утверждение и каждую правку подтверждай дословной цитатой из разрешенного источника. Код
   проверит, что цитата буква в букву есть в источнике.
3. Не объясняй и не предполагай. Если в источниках нет факта, не выводи его из общих знаний, из названий
   файлов или из других заданий: верни статус `needs_human` и вопрос в поле `questions`.
4. Не переноси выводы между заданиями. Что изменено в задаче, определяют только ее записи, ее изменения
   кода и ее тексты интерфейса.
5. Не описывай изменение шире, чем оно записано в источнике. Если в источнике «исправлен порядок пунктов
   меню», в документации меняется порядок пунктов меню, и ничего больше.
6. Одна задача часто содержит несколько записей о разном. Правка нужна только для того, что видит
   пользователь и что описано на страницах задания. Если для записи на страницах нет подходящего места,
   не добавляй новый абзац «на всякий случай»: напиши об этом в `summary`.

## Вопросы и противоречия

Не задавай человеку вопросов в чате во время работы и не жди ответа: он смотрит результат после всех
заданий. Если чего-то не хватает или данные противоречат друг другу, запиши вопрос в поле `questions`
ответа, поставь статус `needs_human` или `recheck` и переходи к следующему заданию. В документацию
вопросы и пояснения не пишутся.

## Как работать быстро

- Начинай с файла `sources/<задача>/changes.md`: в нем все измененные строки кода по задаче. Обычно его
  достаточно. Отдельный патч открывай, только если строка в сводке обрезана.
- Страницу документации не читай целиком: в задании есть заголовки с номерами строк. Открывай нужный раздел.
- Не перечитывай этот файл перед каждым заданием: правила одинаковые.
- Не ищи по папке и не открывай источники других задач.

## Ход работы: файл `progress.md`

Человек следит за работой по файлу `progress.md` в корне папки. Дописывай в конец по одной строке:

- в начале задания: `НАЧАЛ <задание>`;
- после каждого открытого источника: `ШАГ <задание>: <источник> - <что нашел>`;
- в конце: `ГОТОВО <задание>: <статус> - <итог одной фразой>`.

Пиши строку сразу, а не все разом в конце. Те же шаги потом переносятся в `steps` ответа.

## Статусы и второй круг

- `done` - вывод подтвержден источниками;
- `recheck` - вывод есть, но ты в нем сомневаешься: источники противоречат друг другу или изменение можно
  понять двумя способами. Напиши сомнение в поле `recheck_reason`. Человек посмотрит и запустит второй круг;
- `needs_human` - в источниках нет факта, вывод сделать нельзя.

Не выдавай догадку за факт: для этого есть `recheck` и `needs_human`.

В задании второго круга есть раздел «Второй круг» с первым ответом и причиной. Проверь первый ответ заново
по источникам, подтверди или исправь. Первый ответ источником не считается.

## Ответ

Запиши ответ в файл, названный в задании, в формате JSON:

```json
{
  "item": "номер задания",
  "rules": "{{RULES_CODE}}",
  "status": "done, recheck или needs_human",
  "recheck_reason": "только для recheck: в чем сомнение",
  "summary": "одно-два предложения: что изменилось для пользователя и что ты предлагаешь",
  "steps": [
    {"source": "что открыл: источник или страница из задания", "found": "что там нашел, одной фразой"}
  ],
  "decision": "только для заданий decide: doc, rn, langs, screens или skip",
  "evidence": [
    {"source": "источник из списка разрешенных", "quote": "дословная цитата из него"}
  ],
  "edits": [
    {
      "file": "docs/MD_rus/docs/путь/страницы.md",
      "find": "точный фрагмент страницы, который нужно заменить",
      "replace": "новый текст на его месте",
      "what": "что изменено, одной фразой",
      "evidence": [{"source": "источник из списка разрешенных", "quote": "дословная цитата"}]
    }
  ],
  "questions": ["вопросы человеку, если есть"]
}
```

- `rules` - код из этого файла: `{{RULES_CODE}}`. Он показывает, что ты прочитал общие правила.
- `steps` - обязательный журнал: каждый открытый источник и что в нем найдено, по порядку.
- `evidence` на верхнем уровне обязательно для заданий `decide`.
- Источник `changelog` означает записи списка изменений задачи, `i18n` - ее тексты интерфейса, `jira` -
  название и описание задачи. Остальные источники указываются путем, как в списке.

### Как описывать правку

- `find` - фрагмент страницы, скопированный буква в букву, со всеми пробелами и знаками. Он должен
  встречаться на странице ровно один раз: если фраза повторяется, возьми фрагмент длиннее.
- `replace` - текст, который встанет на его место. Чтобы добавить текст, возьми в `find` соседнюю строку
  и повтори ее в `replace` вместе с новым текстом. Чтобы удалить, оставь в `replace` то, что должно остаться.
- Одна правка - одно место на странице, не больше 30 строк нового текста. Большое изменение раздели на
  несколько правок.
- Правка минимальная: в `find` только то, что меняется, и столько соседнего текста, сколько нужно для
  однозначности. Незатронутый текст не переписывай и не переформатируй.
- Сначала правки RU, затем те же по смыслу правки EN.
- Названия элементов интерфейса бери дословно из раздела «Тексты интерфейса» задания для нужного языка и
  ставь в кавычки, как принято на странице. Не используй название, помеченное в задании как удаленное
  или как старое значение.
- Названия продуктов и компонентов пиши только переменными, которые уже есть на странице
  (например, `{{PRODUCT_NAME}}`). Не пиши «LUNA» и «VisionLabs» текстом.
- Скриншотами не занимайся: не выясняй, что на картинках, не ставь меток и не меняй строки с картинками.
  Какие скриншоты нужно проверить, определяет код по измененным разделам.
- Файлы `trace.md`, `screenshots.md` и release notes не трогай и в правках не указывай: их ведет код.

## Как проверяется твоя работа

Код сверяет ответ с реальными данными. Ответ не принимается целиком, если:

- цитаты в `evidence` нет в названном источнике буква в букву;
- в `steps` назван файл, которого нет среди источников и страниц задания;
- страница правки не входит в страницы задания;
- фрагмента `find` нет на странице дословно или он встречается больше одного раза;
- в новом тексте есть название в кавычках, которого нет ни в текстах интерфейса новой версии, ни на
  странице, ни в записях задачи;
- в новом тексте есть комментарий `<!-- -->`, метка скриншота или правка длиннее 30 строк;
- в ответе нет кода правил.

Поэтому перед тем как записать ответ, перечитай каждую цитату и каждый `find` в файле и убедись, что они
стоят там дословно. Не цитируй по памяти.

## Вид задания `decide`: Проверить решение и сразу выполнить его

Решение правил по задаче не подтверждено. В задании записи, основание для проверки и источники.

1. Открой сводку изменений и выясни, что изменилось на экране приложения POINT 2.
2. Проверь продукт: если изменение есть только в файлах с `.point3.` в имени или в файлах, которые
   приложение POINT 2 не использует (это написано в сводке), это другой продукт.
3. Проверь видимость: изменение только отступов, цветов, шрифтов и анимаций в документации не описывается.
   Изменение текста, элементов, порядка действий или поведения - видимое.
4. Выбери одно решение и запиши его в поле `decision`:
   - `doc` - видимое изменение POINT 2: нужна правка документации и строка в release notes;
   - `rn` - исправлена ошибка, которую мог заметить пользователь: только строка в release notes;
   - `langs` - изменился набор языков интерфейса;
   - `screens` - изменилось только оформление: текст не менять, проверить скриншоты;
   - `skip` - другой продукт или пользователь изменения не видит.
5. В `evidence` приведи цитаты, на которых основан вывод.
6. Второго задания по этой задаче не будет. Если решил `doc`, опиши правки в `edits` по разделу
   «Вид задания `write_doc`». Если решил `rn`, `screens` или `skip`, `edits` оставь пустым.

## Вид задания `write_doc`: Написать правку документации

Задача принята: изменение видит пользователь.

1. По сводке изменений и текстам интерфейса выясни, что изменилось на экране: экран, элемент, было -> стало.
2. Найди место на страницах задания. Если раздел подключается через `{% include %}` и нужного файла в
   списке страниц нет, не ищи его сам: верни `needs_human`.
3. Опиши правки в `edits`: сначала RU, затем EN.
4. Если подходящего места нет или не хватает факта, текст не выдумывай: верни `needs_human` с вопросом.

## Вид задания `check_doc`: Проверить документацию после исправления ошибки

Задача - исправление ошибки. В задании перечислены тексты интерфейса, которые исчезли из интерфейса, и места
в документации, где они еще упоминаются.

1. Открой указанные места.
2. Название, которого больше нет в интерфейсе, в документации устарело. Найди в сводке изменений или в
   патче файла переводов, какой текст стоит на этом месте теперь, и опиши замену в `edits` (RU, затем EN).
   Это нужно сделать, даже если основное изменение задачи о другом: устаревшее название - ошибка документации.
3. Если по источникам не видно, чем заменено название, не подбирай похожее по смыслу: перечисли такие места
   в `questions` и оставь их без правки.
4. Если упоминание относится к другому элементу с таким же названием, который не менялся, не трогай его и
   напиши это в `summary`.

## Вид задания `check_langs`: Сверить список языков интерфейса

В задаче менялась локализация.

1. Если в задании есть раздел «Языки интерфейса, доступные пользователям», это главный источник: в нем
   сказано, какие языки добавлены в релизе. Ссылайся на него как на источник `knowledge`.
2. Если такого раздела нет, по файлам настроек приложения из списка источников выясни, какие языки включены,
   и сравни со старым набором: он виден в сводке изменений по строкам с `-`. Не суди по числу файлов переводов.
3. Найди на страницах задания список языков интерфейса. Если он есть и устарел, опиши правку в `edits`.
4. В `summary` напиши, какие языки добавились или убрались. Если набор не изменился, так и напиши. Если
   списка языков на страницах задания нет, `edits` оставь пустым и напиши это в `summary`.

## Вид задания `release_notes`: Формулировки для release notes

Выполняется последним. Файлы release notes собирает код: заголовок, таблицу версий, разделы, метки
разделов. От тебя нужны только формулировки, по одной на задачу.

В ответе вместо `edits` дай поле `lines`:

```json
"lines": [
  {"task": "GUI-1234", "section": "Раздел \"Поиск\"", "ru": "Формулировка на русском.", "en": "Wording in English."}
]
```

1. Для каждой задачи из задания напиши одной фразой, что изменилось для пользователя на экране. Источник -
   записи разработчиков этой задачи в задании и то, что ты сам установил по ней в заданиях этого прохода.
   Название задачи из Jira внутреннее: не переписывай его, оно только подсказывает, о чем задача.
2. Убери названия компонентов, хуков, файлов и кода. Пиши о результате, а не о реализации: не «переведены на
   resetFilters», а что теперь происходит на экране.
3. Обычно одна строка на задачу. Если у задачи несколько разных видимых изменений, дай несколько строк с тем
   же `task`, не больше четырех. Не объединяй разные изменения через точку с запятой и не теряй ни одного
   видимого изменения.
4. `section` - раздел интерфейса, к которому относится изменение. Выбери его из списка разделов в задании,
   слово в слово. Если изменение общее или касается нескольких разделов, выбери «Общее».
5. Для задач с пометкой «решение принимаешь ты» давай строки, только если в своем ответе по этой задаче ты
   решил `doc`, `rn` или `langs`. Иначе строк для нее не давай.
6. Если в задании есть раздел о языках интерфейса, строку о языках пиши по нему: какие языки добавлены.
7. `en` - перевод `ru` в стиле образца прошлого релиза.
8. Если по задаче строка не нужна (пользователю изменение не видно или оно уже описано другой строкой),
   не придумывай ее: добавь задачу в поле `no_line` с причиной:

   ```json
   "no_line": [{"task": "GUI-1234", "reason": "почему строки нет, одной фразой"}]
   ```

   Причину код покажет человеку. Задача без строки и без `no_line` - ошибка ответа.
9. Если из записей непонятно, что изменилось для пользователя, не выдумывай: дай самую близкую к записи
   формулировку и назови задачу в `questions`.

В какой раздел файла пойдет строка, «Изменения» или «Исправленные ошибки», решает код по типу записей.

`steps`, `evidence` и `edits` для этого задания не нужны.
