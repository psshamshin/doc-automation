# Правила пайплайна doc-automation (группы А-З)

Полный список правил в том виде, в каком они реализованы. Старые формулировки не удаляются: у каждого
измененного правила рядом стоит пометка «Изменение N», а в разделе [История изменений](#история-изменений)
записано, что было, что стало и на какой задаче нашлась ошибка. Источники: `knowledge/rules.json`,
`knowledge/doc_map.json`, `pipeline/*.py`, `AGENTS.md`, `agent/prompts/*.md`.

Правила применяются по порядку групп. Порядок групп: (А) границы -> (Б) сборка задач -> (В) продукт -> (Г) видимость -> (Д) вид изменения ->
(Е) место в доке -> (И) достоверность решения -> (Ж) написание -> (З) скриншоты.

Группы А-Е и И выполняет код (команда `collect`). Группы Ж и З выполняет агент по заданиям из
`agent/prompts/` (команда `agent`). Агент также проверяет решения, достоверность которых по группе И низкая.

Как читать документ:

- **ID** - буква группы и номер. Номера не переиспользуются и не сдвигаются: удаленное или
  замененное правило сохраняет свой номер и остается в документе.
- **Где** - файл и функция, в которых правило реализовано.
- Изменения правил записываются в разделе [История изменений](#история-изменений) в формате
  «старая формулировка → новая формулировка → причина (номер задачи)».

## А. Границы релиза

| ID | Правило | Где |
| --- | --- | --- |
| А1 | Границы релиза задаются версиями интерфейса (point-ui): нижняя - версия предыдущего релиза, верхняя - текущего. Версии читаются из кода: поле `version` в `apps/point/package.json` в двух папках с кодом; меньшая версия - предыдущий релиз (изменение 11). **Изменение 5:** было - значения `ui_version_lower`, `ui_version_upper` из файла настроек релиза. | `pipeline/releases.py`, `ui_version_of`; `pipeline/layout.py` |
| А2 | Из ченджлога берутся все версии строго выше нижней границы и не выше верхней, включая патчи: `lower < v <= upper`. Версии сравниваются как semver. | `pipeline/changelog.py`, `select_range` |
| А3 | Версии за пределами границ не учитываются. Первые 10 отброшенных версий записываются в `01_changelog.json` (`outside_range_versions`) для контроля. | `pipeline/changelog.py`, `collect` |

Уточнения реализации:

- Ченджлог читается из новой версии кода: `apps/point/CHANGELOG.md` в папке с новым кодом (путь задан в
  `pipeline/product.py`).
- Разделы ченджлога дают тип записи: «Добавлено» → `add`, «Изменено» → `change`, «Исправлено» → `fix`,
  «Удалено» → `remove`, остальное → `other`.
- Дифф кода строится между двумя папками целиком (старый и новый код), без git. Файл считается
  измененным, если отличается размер или SHA-1.
- Из диффа исключаются (`diff_exclude_globs`): `*/node_modules/*`, `*.map`, `package-lock.json`,
  `CHANGELOG.md` на любом уровне.

## Б. Сборка единиц изменения

| ID | Правило | Где |
| --- | --- | --- |
| Б1 | Записи ченджлога группируются по номеру задачи. Единица изменения = одна задача, все ее записи оцениваются вместе. | `pipeline/units.py`, `build_units` |
| Б2 | К задаче привязываются измененные файлы кода, на которые указывают ее записи (см. ниже). | `pipeline/units.py`, `files_for_entry` |
| Б3 | Запись без номера задачи - отдельная единица с ID `NOTASK:<версия>#<номер записи>`. | `pipeline/units.py`, `build_units` |
| Б4 | Одна задача может дать несколько правок доки и одну строку в release notes. Кодом не проверяется, выполняет агент. | `agent/prompts/write_doc.md`, `agent/prompts/release_notes.md` |

### Б1. Как определяется номер задачи

- Формат: `GUI-123`, `PASS-123`, `LP-123`, `VL-123`, допустимо в обратных кавычках.
- Номер должен стоять в начале записи: не дальше 20-го символа после тегов. Номер в середине текста
  задачей записи не считается.
- Теги - подряд идущие `[...]` в начале записи. Продолжение записи на следующей строке приклеивается к тексту.

### Б2. Как файл привязывается к записи

Привязка идет по тегам записи и по именам в тексте. Все сработавшие способы складываются.

1. **По тегам, первый тег - имя пакета** (`package_dirs`: `monokit`, `pages`, `shared`, `api`,
   `api-bindings`, `permissions`). Остальные теги - подпути: `packages/<пакет>/<тег>` и
   `packages/<пакет>/src/<тег>`. Запись с одним тегом пакета (`[pages]`) по тегам не привязывается:
   тег слишком широкий.
2. **По тегам, первый тег - не пакет.** Каждый тег ищется в приложении: `apps/point/src/app/<тег>`,
   `apps/point/src/<тег>`, `apps/point/src/components/<тег>`.
3. **Служебные теги не дают привязки** (`ignore_tags`): `point`, `point2`, `point3`, `app`, `cypress`,
   `e2e`, `tests`, `vitest`, `deps`, `build`.
4. **Алиасы тегов** (`tag_aliases`): `video analytics`, `videoanalytics` → `pages/video-analytics`.
5. **Запасной вариант**, если по тегам пакета ничего не найдено: последний сегмент тега (от 4 символов)
   ищется как каталог или имя файла внутри пакета. Пример: `[monokit][page-header]` →
   `packages/monokit/widgets/page-header/…`.
6. **По именам компонентов и хуков**: имена в обратных кавычках, слова в CamelCase в тексте, kebab-тег,
   переведенный в CamelCase (`event-list` → `EventList`). Имя (от 4 символов) должно совпасть с именем
   файла без расширения.

**Изменение 7.** Файлы другого продукта в доказательства задачи не входят, даже если на них указывает
значимая запись. Файл другого продукта - файл с меткой в имени (`.point3.`, список
`product.other_product_file_markers`) или файл из папки другого приложения (`apps/point3`,
`apps/clementine`, `apps/luna`, список `product.other_app_dirs`). Было: такие файлы входили в
доказательства наравне с остальными.

Файлы, на которые не указала ни одна запись, попадают в `unattributed_files` (`05_units.json`, раздел
отчета «Файлы без привязки»). Их просматривает агент на шаге 3.

### Признаки записи

Для каждой записи ченджлога вычисляются пять признаков. Где: `pipeline/units.py`, `entry_flags`, `_markers`.

| Признак | Условие |
| --- | --- |
| `other_product` | В записи найден маркер другого продукта (см. ниже). |
| `test` | Среди тегов есть `cypress`, `e2e`, `tests` или `vitest` (`test_tags`). |
| `ui` | В тексте есть слово из `ui_keywords`. |
| `technical` | В тексте есть слово из `technical_keywords` и нет ни одного слова из `ui_keywords`. **Изменение 2:** либо в тексте есть слово из `technical_strong_keywords` и ссылка на код; тогда слова интерфейса не учитываются. |
| `significant` | **Изменение 1.** Значимая запись: нет признаков `other_product`, `test` и `technical`. |

Маркеры другого продукта (`product.text_markers`). Поиск идет по тексту записи и ее тегам, без учета регистра:

| Продукт | Срабатывает | Не срабатывает (исключения) |
| --- | --- | --- |
| `point3` | Тег `point3`; либо в тексте `.point3`, `point 3` / `point3`, `поинт 3` / `поинт3`. | В тексте есть «point и point3», «point3 and point» и подобное, либо `point2` / `point 2`. Тег `point3` срабатывает всегда, исключения на него не действуют. |
| `clementine` | Тег `checks`; либо в тексте `clem…`, `клементин…`. | Исключений нет. |

`ui_keywords`: отображ, кнопк, фильтр, поле, поля, страниц, меню, раздел, валидац, подтвержд, сообщени,
модальн, колонк, таблиц, вкладк, форм, пользовател, заголов, прокрутк, скролл, «тема », тему, локал, язык,
адресн, сброс, сохран, загрузк, создани, название, подсказ, плейсхолдер, placeholder, обязательн, интерфейс.

`technical_keywords`: рефакторинг, «переведен на», вынесен, перенесен, типизац,
тест, eslint, линтер, зависимост, сериализац, хук, redux, контекст, адаптер, fsd, сборк, скелетон,
storybook, unused, неиспользуем, переиспользуем, «компонент \`», перепривязан, импорт, «ложные ошибки».

`technical_strong_keywords` (изменение 2): рефакторинг, «переведен на», вынесен, перенесен, перепривязан.
Это слова о переносе и переводе кода. Они делают запись технической, только если в записи есть ссылка на
код (`code_reference_regex`): текст в обратных кавычках, путь латиницей со знаком `/` или имя в CamelCase.
Пример: «Перенесен компонент селекта ... в пакет monokit/shared ... на других страницах» - техническая,
хотя в тексте есть слово «страниц». Запись «Кнопка перенесена в меню» ссылки на код не содержит и
технической не становится.

Слова ищутся как подстроки без учета регистра. Слова «переведен на» и «перенесен» записаны в конфиге в двух
написаниях: через «е» и через «е с двумя точками».

### Значимые записи (изменение 1)

Значимая запись - запись без меток другого продукта, не тестовая и не техническая.

- **Было:** файлы, строки интерфейса, проверка навигации, роутов и прав, класс Д и кандидаты страниц
  считались по всем записям задачи без меток другого продукта, включая тестовые и технические.
- **Стало:** все эти доказательства считаются только по значимым записям и по файлам, привязанным к ним.
  Поле `relevant` у файла в `05_units.json` означает «привязан к значимой записи». В отчете у незначимых
  записей стоит пометка «не учитывается: другой продукт / тест / техническая».
- **Причина:** GUI-4106, GUI-4134, GUI-4057 - в доку попадали рефакторинг и перенос кода.

Правила группы В изменение не затрагивает: продукт по-прежнему определяется по всем записям без меток
другого продукта. Техническая правка тоже принадлежит продукту; отбрасывает ее группа Г.

## В. Продукт: касается ли POINT 2

Правила применяются по порядку, первое сработавшее решает. Где: `pipeline/units.py`, `decide_product`.

Файлы учитываются только по записям без маркеров другого продукта: общие barrel-экспорты делают
«достижимыми» из POINT 2 и компоненты point3.

| ID | Сигнал | Решение |
| --- | --- | --- |
| В1 | У задачи в выгрузке Jira в начале названия есть префикс `[point]` (`jira_point_tag`). | `point2` |
| В2 | У задачи в выгрузке Jira в начале названия есть префиксы в квадратных скобках, но `[point]` среди них нет. | `other` - отбросить |
| В7 | Все записи задачи помечены маркером другого продукта. | `other` - отбросить |
| В3 | Все файлы записей без маркеров лежат в `apps/point/`. | `point2` |
| В4 | Все файлы записей без маркеров лежат в приложениях других продуктов: `apps/point3`, `apps/clementine`, `apps/luna` (`other_app_dirs`). | `other` - отбросить |
| В5 | Хотя бы один файл записей без маркеров достижим из `apps/point/src` по графу импортов и в его пути нет `.point3.` (`other_product_file_markers`). | `point2` |
| В6 | У записей без маркеров файлы есть, но ни один не достижим из `apps/point`. | `other` - отбросить |
| В8 | Не используется. Номер зарезервирован, в коде правила нет. | - |
| В9 | Остаток: файлы есть только у записей с маркерами другого продукта, либо файлы не привязаны и маркеров нет. | `needs_review` - решает агент |

Строки таблицы стоят в порядке применения: В1 → В2 → В7 → В3 → В4 → В5 → В6 → В9.

Уточнения реализации:

- В1 и В2 работают, только если задача есть в выгрузке Jira и у ее названия есть хотя бы один префикс
  `[...]`. Задача без префикса или без выгрузки идет дальше по В7-В9.
- Выгрузка Jira читается из папки `jira/`: XML (Export → XML), CSV (Export → CSV, заголовки RU или EN),
  JSON (список объектов или `{"issues": [...]}`), TXT / MD (строка `GUI-1234 [point] Название`, далее
  описание до следующего ключа). Префиксы приводятся к нижнему регистру. Где: `pipeline/jira.py`.
- Достижимость (В5, В6) - обход графа импортов от всех файлов `apps/point/src` (`entry_dirs`), по старой и
  по новой версии кода, результаты объединяются. Разбираются `import … from`, `import '…'`, `import()`,
  `require()`; пути - относительные, workspace-пакеты `@vlabs/*` и `@vlapps/*`, `paths` из `tsconfig.json`
  пакета. Это эвристика на регулярных выражениях: неразрешенные внутренние импорты считаются и выводятся в
  отчет. Где: `pipeline/import_graph.py`.

## Г. Видимость для пользователя

Оцениваются только значимые записи и привязанные к ним файлы (изменение 1; было: записи без маркеров
другого продукта и их файлы). Правила применяются по порядку, первое сработавшее решает. Где: `pipeline/units.py`, `decide_visibility`.

| Шаг | ID | Сигнал | Решение |
| --- | --- | --- | --- |
| 1 | Г4 | Нет значимых записей: только другой продукт, тесты и технические записи. Действует, даже если менялись файлы переводов. | `not_visible` |
| 2 | Г4 | Объединен с шагом 1 (изменение 1). Было два шага: «нет записей про POINT 2» и «все записи про POINT 2 - тестовые или технические». | `not_visible` |
| 3 | Г1 | В файлах значимых записей изменились строки интерфейса: появились, исчезли или изменились при том же ключе. | `visible` |
| 4 | Г2 | Изменен файл, в пути которого есть `/navigation/`, `/routes` или `/permissions/`. | `visible` |
| 5 | Г4 | Все файлы задачи относятся к невидимым категориям (`invisible_categories`): `test`, `changelog`, `build`, `ci`, `types`, `mocks`, `docs_internal`. | `not_visible` |
| 6 | Г3 | Все файлы задачи - стили (`style`) и, возможно, невидимые категории. | `style_only`: в доку не идет, возможна пересъемка скрина |
| 6а | Г3 | **Изменение 8.** Все значимые записи - из раздела «Исправлено», и в каждой есть слово из `style_keywords`: стил, отступ, шрифт, цвет, анимац. | `style_only`: в доку не идет, возможна пересъемка скрина |
| 7 | Г5 | В значимых записях есть слова из `ui_keywords`, и все такие записи - из раздела «Исправлено». | `visible` |
| 8 | Г2 | В значимых записях есть слова из `ui_keywords`, и среди таких записей есть не только исправления. | `visible` |
| 9 | - | Ни одно правило не сработало. | `unknown` - решает агент |

Уточнения по Г1 (строки интерфейса). Где: `pipeline/i18n_extract.py`, `pipeline/units.py`, `build_units`.

- Файлы переводов (`i18n.file_globs`): `*/i18n.ts`, `*/i18n.js`, `*/i18n/*.ts`, `*/translations/*.ts`,
  `*/translations/*/*.ts`.
- Локаль определяется по имени экспорта (`locale_export_names`): ru - `ru`, `ruRu`, `entitiesRu`;
  en - `en`, `enUs`, `entitiesEn`; pt - `ptBr`, `entitiesPtBr`; es - `esEs`, `entitiesEsEs`.
- В дифф идут только локали `ru` и `en` (`diff_locales`).
- Дифф строится двумя способами: по значениям (какие тексты появились и исчезли в локали) и по ключам
  (у того же ключа в том же файле поменялся текст).
- Значения-ссылки вида `$t(key)` и пустые значения текстом не считаются.
- Перенос строки между файлами изменением не считается: «добавленный» текст отбрасывается, если он был
  где-либо в старой версии; «удаленный» - если он есть где-либо в новой; «измененный» - если старое
  значение есть в новой версии, а новое было в старой.
- **Изменение 7.** Новый или измененный текст не считается доказательством, если он используется в коде и
  все места использования - файлы другого продукта. Использование ищется по вызову с ключом перевода,
  например `t('shared:personCard.unavailable_lists')`; окончания множественного числа (`_one`, `_few`,
  `_many`, `_other`) отбрасываются. Если вызов не найден, текст остается доказательством. Такие тексты
  записаны в `05_units.json` в поле `i18n.other_product`. Где: `pipeline/i18n_extract.py`, `key_usage`;
  `data/03_i18n_usage.json`.
- Для задачи учитываются только строки из файлов, привязанных к ее значимым записям (изменение 1; было:
  к записям без маркеров другого продукта).

## Д. Класс изменения и действие

### Решение по единице

Итоговое действие `decision.action`. Первое сработавшее решает. Где: `pipeline/units.py`, `action_of`.

| Шаг | Условие | Действие | В отчете |
| --- | --- | --- | --- |

## И. Достоверность решения

Правила групп В-Д всегда выдают какое-то решение. Группа И определяет, можно ли на него опереться без
проверки. Где: `pipeline/confidence.py`, `assess`. Результат: `data/07_review.json`, `review.md`.

**Определение.** Достоверность решения по задаче низкая, если выполнен хотя бы один критерий вида
«решение». Иначе достоверность высокая. Критерии вида «место» достоверность не снижают: решение принято,
но место в документации не определено, и это замечание автору текста.

| ID | Вид | Критерий | Почему решение не подтверждено |
| --- | --- | --- | --- |
| И1 | решение | Продукт не определен (В9). | Нет ни файлов, ни меток продукта. |
| И2 | решение | Видимость не определена (ни одно правило группы Г не сработало). | Нет изменений текстов, навигации и прав, в записях нет слов об интерфейсе. |
| И3 | решение | Видимость определена только по словам в записи (правило Г5 или Г2 по тексту), и к значимым записям не привязан ни один файл кода, который использует приложение. **Изменение 9:** было - всегда, когда видимость определена по словам. | Нет ни текстов интерфейса, ни измененного кода приложения: слово в записи ничем не подтверждено. |
| И4 | решение | Видимость по Г1, но все изменившиеся тексты интерфейса привязаны и к другим задачам, и ни один из них не назван дословно в записях этой задачи. | Файл переводов общий для нескольких задач: текст мог изменить другой. |
| И5 | решение | Продукт POINT 2, но не меньше половины файлов кода значимых записей приложение не использует. **Изменение 9:** файлы с признаком другого продукта сюда больше не входят, они исключены из доказательств изменением 7. | Изменение, возможно, сделано для другого продукта. |
| И6 | место | Вид изменения поставлен по умолчанию (Д3). | Признаки классов Д2-Д9 не найдены. |
| И7 | место | Нужна правка или проверка документации, но страница по карте не найдена (Е1). | - |
| И8 | место | Страниц-кандидатов больше трех. | Карта дала слишком широкий результат. |

Уточнения:

- Критерии И3-И6 проверяются только у задач, которые не отброшены. Отброшенная задача с определенным
  продуктом и видимостью имеет высокую достоверность.
- В И4 текст считается общим, только если вторая задача сама идет «в доку + RN» или «RN + проверить доку».
- У задачи с низкой достоверностью в файле проверки по умолчанию стоит отметка «Агенту».

### Проверка человеком

Где: `pipeline/validation.py`. Файл: `output/<набор>/review.md`. У каждой задачи одна из трех отметок.
Агент не запускается, пока в файле нет отметки «Проверено».

| Отметка | Решение правил | Что будет с задачей |
| --- | --- | --- |
| Принять | любое, кроме «не определено» | Выполняется решение правил |
| Принять | не определено | Задачу проверяет агент |
| Отклонить | задача взята в работу или не определена | Задача в работу не берется |
| Отклонить | отброшено | Задачу проверяет агент |
| Агенту | любое | Задачу проверяет агент |

### Что делает агент после проверки человеком

Где: `pipeline/agent.py`, `kinds_for`. Агент получает отдельное задание на каждую задачу, а не весь релиз.

| Итог проверки | Задание агенту | Когда |
| --- | --- | --- |
| задачу проверяет агент | `decide`: проверить решение по коду | всегда |
| в доку + RN | `write_doc`: написать правку RU и EN | всегда |
| RN + проверить доку | `check_doc`: проверить, не описано ли старое поведение | только если в документации нашлись старые тексты интерфейса (Е3) |
| RN + проверить список языков | `check_langs`: сверить список языков | всегда |
| проверить скрины | нет | скриншоты проверяет человек |
| не брать в работу | нет | - |
| есть хотя бы одна задача для release notes | `release_notes`: одно задание на релиз | после остальных |

Все задания готовятся сразу (изменение 14). Задание `decide` включает и правку, если агент решил, что она
нужна. Было: сначала выполнялись задания `decide`, затем по итоговым решениям строились остальные.

## История изменений

Правила из этого документа не удаляются, номера не меняются. Каждое изменение записано здесь и в поле
`_changes` файла `knowledge/rules.json`.

Формат записи: было, стало, причина (номер задачи, на которой нашлась ошибка), где в коде.

### Изменение 1 - 2026-11-11 - доказательства только по значимым записям

Затронуты: Б2, Г1-Г5, черновой класс Д2-Д9, Е1, Е3.

- **Было:** доказательства (файлы, строки интерфейса, навигация, роуты, права, класс Д, кандидаты страниц,
  поиск старых текстов в доке) собирались по всем записям задачи без меток другого продукта, включая
  тестовые и технические.
- **Стало:** доказательства собираются только по значимым записям: без меток другого продукта, не тестовым,
  не техническим. Если значимых записей нет, задача не видна (Г4), даже если менялись файлы переводов.
- **Причина:** GUI-4106, GUI-4134, GUI-4057. В доку попадали рефакторинг и перенос кода: техническая
  запись приносила в задачу файлы переводов, и срабатывало Г1.
- **Где:** `pipeline/units.py`: `entry_flags`, `significant_entries`, `build_units`, `decide_visibility`,
  `decide_class`.

### Изменение 2 - 2026-11-11 - признак «техническая запись»

- **Было:** запись техническая, если в тексте есть слово из `technical_keywords` и нет слов из `ui_keywords`.
- **Стало:** дополнительно запись техническая всегда, если в тексте есть слово из
  `technical_strong_keywords` (перенос или перевод кода) и ссылка на код по `code_reference_regex`.
  Слова интерфейса в такой записи не учитываются: они описывают место кода, а не изменение на экране.
- **Причина:** GUI-4057 (запись о переносе компонента селекта: слово «страницах») и GUI-4134 (запись о
  переводе `StatisticPage` на `useAppTheme`: слова «страницы», «перезагрузки»). Из-за слов интерфейса
  записи о переносе кода считались значимыми.
- **Где:** `knowledge/rules.json`: `visibility.technical_strong_keywords`, `visibility.code_reference_regex`;
  `pipeline/units.py`: `entry_flags`.

### Изменение 3 - 2026-11-11 - Д7

- **Было:** Д7, если есть запись из раздела «Удалено» или в тексте любой записи есть слова об удалении.
- **Стало:** Д7, если есть значимая запись из раздела «Удалено» или слова об удалении есть в значимой
  записи не из раздела «Исправлено». В записи-исправлении слова об удалении описывают способ исправления.
- **Причина:** GUI-4134. Исправление сброса темы получало класс Д7 из-за слов «Удалена обертка» и
  технической записи «Удален ThemeContext».
- **Где:** `pipeline/units.py`: `decide_class`.

### Изменение 4 - 2026-11-11 - Д9 и действие для локализации

Затронуты: Д9, решение по единице, Е1.

- **Было:** Д9 только если в коде появился каталог новой локали и в тексте есть слова о локалях или тег
  `i18n`. Действие для Д9 общее: «в доку + RN». Кандидаты страниц - по всем файлам задачи.
- **Стало:** Д9 также если значимая запись с тегом из `class.locale_tags` упоминает локали или языки
  (`class.locale_keywords`). Для Д9 введено действие `rn_and_check_langs`: строка RN и проверить список
  языков в доке. Кандидаты страниц для него - только области из `class.locale_doc_areas`.
- **Причина:** GUI-4106. Переделка переводов давала класс Д3, действие «в доку + RN» и 18
  страниц-кандидатов. Условие на тег нужно, чтобы не задеть GUI-4067: там в тексте есть «во всех четырех
  локалях», но задача про поиск.
- **Где:** `knowledge/rules.json`: `class`; `pipeline/units.py`: `decide_class`, `action_of`, `doc_candidates`.

### Изменение 5 - 2026-11-11 - версии без файла настроек

Затронуты: А1, Д10.

- **Было:** границы релиза, версия документации, имя файла release notes, дата и версии компонентов
  задавались вручную в `config/release-<релиз>.json`.
- **Стало:** версии читаются из входных данных: версия интерфейса из `apps/point/package.json`, версия
  документации предыдущего релиза из последнего файла release notes, версия нового релиза из базы знаний
  `knowledge/releases.json` по версии интерфейса. Постоянные имена папок и компонентов записаны в
  `pipeline/product.py`. Файла настроек релиза нет.
- **Причина:** настройки приходилось править руками для каждого запуска; ошибка в одной версии давала
  неверные границы релиза.
- **Где:** `pipeline/product.py`, `pipeline/releases.py`, `pipeline/layout.py`.

### Изменение 6 - 2026-11-11 - черновик собирает код, агент работает по заданиям

Затронуты: Д10, Ж6, Ж8, новая группа И.

- **Было:** агент проходил все задачи релиза в четыре шага (анализ, место, правки, release notes) и сам
  решал, каким решениям правил доверять.
- **Стало:** код заменяет версию интерфейса в документации, собирает черновик release notes из записей
  ченджлога и оценивает достоверность каждого решения по критериям группы И. Человек проверяет решения в
  файле проверки. Агент получает отдельные задания: проверку решений с низкой достоверностью и написание
  текста.
- **Причина:** агент тратил время на задачи, которые правила решают однозначно, а результат нельзя было
  проверить до его запуска.
- **Где:** `pipeline/confidence.py`, `pipeline/draft.py`, `pipeline/validation.py`, `pipeline/agent.py`.

### Изменение 7 - 2026-11-12 - файлы и тексты другого продукта не доказательство

Затронуты: Б2, Г1-Г3, Е1.

- **Было:** файлы с меткой другого продукта в имени (`.point3.`) и файлы из папок других приложений
  входили в доказательства задачи, если на них указывала значимая запись. Новый текст интерфейса считался
  доказательством видимости независимо от того, где он используется.
- **Стало:** файлы другого продукта в доказательства не входят. Новый или измененный текст интерфейса не
  считается доказательством, если он используется в коде и все места использования - файлы другого продукта.
- **Причина:** GUI-4057. Тексты «N списков недоступны» использует только `ListsPreview.point3.tsx`, но
  задача считалась видимой в POINT 2 по Г1.
- **Где:** `pipeline/units.py`: `is_other_product_path`, `build_units`; `pipeline/i18n_extract.py`:
  `key_usage`.

### Изменение 8 - 2026-11-12 - Г3 по тексту записи

- **Стало:** Г3 также, если все значимые записи - исправления и в каждой есть слово из

Затронуты: Д4, Е3, Ж8.

### Изменение 13 - 2026-11-12 - агент работает в отдельной папке, ответы проверяются по цитатам

Затронуты: Ж4 (факты только из источников), Ж6.

- **Было:** агент работал в папке проекта и получал пути к данным сбора. Запрет выдумывать был только
  в тексте задания. Ответ принимался, если в нем были обязательные поля.
- **Стало:** для агента собирается отдельная папка, где есть только задания, рабочая копия документации и

- **Стало:** все задания готовятся сразу, агент проходит их один раз: задание на проверку решения включает

- **Где:** `pipeline/agent.py`: `build_queue`, `verify_evidence`, `verify_pages`, `verify_release_notes`;

  номерами строк.
- **Причина:** агент работал долго, было не видно, чем он занят; сомнительные выводы выдавались за
  подтвержденные.
- **Где:** `pipeline/agent.py`: `build_digest`, `_page_outline`, `run`, `summary_md`;
